핵심 결정

관계 선택을 단순한 UI 필터가 아니라 과금·캐시·AI·저장의 공통 입력으로 취급합니다.

추천 방향: 관계 메타데이터를 request key v2에 포함하고, DB 컬럼 추가 없이 기존 person1_info JSONB에 저장합니다. 서버는 관계 없는 구버전 요청을 romantic으로 처리합니다.
  • 기본값은 연인, 분석 비용 10포인트 유지
  • 기존 저장 결과는 삭제·재해석하지 않고 계속 열람
  • 새 결과는 중립 태그, 파서는 구·신 태그 동시 지원
  • Edge Function을 먼저 하위 호환 배포한 후 앱 출시
  • 앱 코딩 전에 관계 선택 화면 디자인 승인

데이터·캐시 계약

관계가 다르면 같은 두 사람이어도 다른 분석입니다.

type GunghapRelationship = {
  type: 'spouse' | 'romantic' | 'friend' | 'parent_child'
      | 'siblings' | 'coworker' | 'manager_report'
      | 'owner_employee' | 'business_partner';
  person1Role?: 'parent' | 'child' | 'manager'
              | 'report' | 'owner' | 'employee';
};

정규화 request key v2 입력

{
  "schemaVersion": 2,
  "relationship": { "type": "manager_report", "person1Role": "manager" },
  "person1": { "...": "normalized" },
  "person2": { "...": "normalized" },
  "language": "ko",
  "calendarType": "solar"
}
  • 관계 타입 또는 방향 역할이 바뀌면 다른 키
  • 대칭 관계의 불필요 역할은 정규화 시 제거
  • 새 키는 기존 연애 캐시와 분리
  • 관계 없는 과거 행은 연인으로 표시
  • DB migration·DELETE·과거 행 일괄 업데이트 없음

입력부터 결과까지

관계 선택을 먼저 인지시키되 두 사람 입력 흐름은 그대로 유지합니다.

01관계 선택
02방향 역할 선택
03두 사람 정보
0410P 분석·캐시
05관계별 결과·공유

입력 화면

  • 가격/설명 카드 아래, 첫 번째 사람 카드 위에 관계 섹션
  • 개인·가족 5종과 업무 4종으로 시각 그룹
  • 방향 관계만 역할 토글 표시
  • 역할 전환은 사람 데이터를 교환하지 않음
  • 320px, 390px, Z Fold7 펼침에서 칩 잘림 금지

결과 화면

  • 형제·자매 관계 분석, 직장 동료 협업 분석처럼 제목 분기
  • 관계 배지와 방향 역할을 이름 옆에 표시
  • 공유 이미지에도 동일 관계·역할 포함
  • 내부 점수 필드는 유지하되 사용자 라벨은 관계별 매핑

하위 호환: 파서는 v2 태그를 우선하고 기존 종합궁합·감정연애·결혼가정... v1 태그도 계속 읽습니다.
  • 연애 관계가 아니면 사랑·결혼을 기본 전제로 삼지 않음
  • 부모·자녀 관계에서 아동 성격과 양육 결과를 운명으로 단정하지 않음
  • 직장 관계에서 채용·해고·차별·권력 남용을 정당화하지 않음
  • 사업 관계에서 투자 성공을 보장하지 않음
  • 섹션당 2~3문단으로 줄여 지연·잘림 위험 통제
